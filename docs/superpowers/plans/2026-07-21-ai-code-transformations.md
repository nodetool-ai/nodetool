# Code Node AI Authoring — Implementation Plan

**Goal:** Make the existing Code Node easier to reach for. Today it is powerful but expects you to write JavaScript and to discover handles by referencing undeclared identifiers. Add AI authoring, explicit typed handles, and a preview loop so a user can describe the result they want and get working code — instead of writing it themselves, or searching the catalog for nodes that might fit and wiring them together. Describing the result is faster than finding and connecting the chain.

**Nothing is removed.** The Code Node keeps every capability it has today: `fetch`, workspace access, secrets, `uuid`, `sleep`, asset conversion, persistent `state`, `yield` streaming, dynamic inputs and outputs, AST handle inference, Monaco editing, and the snippet catalog. AI authoring is an additional way to write the code, not a restricted variant of the node.

**Architecture:** Keep `nodetool.code.Code` unchanged as the execution node. Add an optional AI authoring experience, persisted input/output type metadata, and a structured LLM generation service. “Transformation” describes how code is authored, not a saved node mode or restricted runtime category. Do not add another subgraph, workflow-node, or iterator abstraction in Phases 1–3.

**Primary user:** A visual-workflow user who can describe a data change but does not want to write JavaScript or search for several type-compatible nodes.

**Tech stack:** TypeScript, React, Zustand, TanStack Query, ReactFlow, Fastify/tRPC, Zod, QuickJS WASM, Vitest, Jest, Playwright.

---

## Problem

Simple transformations take too long to build because users must:

- Know which small functional node exists.
- Find it in a large node catalog.
- Check whether its input and output handles match the surrounding nodes.
- Chain several nodes when no single node matches the task.
- Fall back to code without help from graph types or sample values.

The first release should answer one question:

> I have values with these types. How do I produce the typed value needed here?

## What exists today

This plan does not introduce the Code Node itself. NodeTool already has a universal Code Node and most of the execution and editor infrastructure needed for the first phase.

| Existing capability | Current implementation | How this plan uses it |
|---|---|---|
| Universal JavaScript Code Node | `packages/code-nodes/src/nodes/code-node.ts` as `nodetool.code.Code` | Keep it as the only runtime node, with the same APIs whether code was written by a person, generated by AI, or created from a snippet. |
| Sandboxed JavaScript runtime | `packages/agents/src/js-sandbox.ts`, using QuickJS WASM | Keep the existing runtime surface. Export a canonical capability manifest so prompts and help describe it accurately. |
| Dynamic Code Node inputs and outputs | `CodeNode.supportsDynamicInputs`, `supportsDynamicOutputs`, `dynamic_properties`, and `dynamic_outputs` | Persist typed `dynamic_inputs`, enrich output metadata, and stop relying on inferred `any` handles when an explicit contract exists. |
| Manual Code Node editor | `web/src/components/node_types/CodeBody.tsx` with Monaco | Keep it available for every Code Node. Add AI authoring and contract controls around it rather than creating a separate node state. |
| JavaScript handle inference | `web/src/utils/codeOutputInference.ts` | Keep it for Code Nodes without an explicit contract. An explicit saved contract takes precedence regardless of how the code was authored. |
| Built-in Code Node snippets | `web/src/config/codeSnippets.ts`, `snippetMetadata.ts`, and `instantiatePaletteNode.ts` | Preserve the existing snippet catalog and fold snippets into the same Code Node authoring experience in Phase 2. |

| Provider abstraction and tracing | `BaseProvider.generateMessageTraced` in `packages/runtime` | Reuse provider resolution, cancellation, usage, cost, and tracing while adding a redacted-content policy. |

| Workflow persistence | Protocol graph schemas plus `reactFlowNodeToGraphNode.ts` and `graphNodeToReactFlowNode.ts` | Extend the existing graph shape and converters; do not create a separate transformation document format. |
| Subgraphs, workflow nodes, and iteration | `packages/core-nodes/src/nodes/subgraph.ts`, `workflow.ts`, and `control.ts` | Leave their ownership and runtime behavior unchanged through Phases 1–3. |

The existing Code Node already:

- Runs on browser and server platforms.
- Accepts user-named dynamic inputs and outputs.
- Injects dynamic inputs as JavaScript variables.
- Returns named outputs from an object.
- Supports a timeout, captured console output, persistent `state`, and Code Node `yield` behavior.
- Exposes host bridges including `fetch`, workspace access, secrets, UUID generation, sleep, and asset conversion.

AI-authored code uses that same runtime surface. The generator targets local data reshaping by default, but the resulting node remains an ordinary, editable Code Node.

## What this plan adds

- A non-programmer AI authoring dialog and compact contract summary for the existing Code Node.
- Explicit, saved, ordered, typed input and output contracts.
- A tool-call-based LLM service that produces validated code plus metadata.
- Preview, repair, saved tests, and later reusable versioned definitions.

It does not add another JavaScript executor in Phases 1–3, and it does not take anything away from the Code Node.

Two Phase 1 limits are worth stating precisely, because both are easy to misread as feature cuts:

- The **generator** writes local data-reshaping code only, and rejects obvious host-API, `state`, and `yield` use. That constrains what the AI produces on the first pass. The resulting node is an ordinary Code Node with the full API, and a user can add any of it by editing. Phase 2 extends the generator itself.
- Task 1.2 **stops the assistant prompt from advertising lodash, Day.js, Cheerio, CSV Parse, and Validator**, which the sandbox does not currently expose. These were added to the sandbox once and deliberately stripped again in `7db9b4ccd` ("strip libs from JS sandbox, move them to workflow nodes"); the prompt was never updated to match. Task 1.2 realigns the prompt with the runtime as it is today. It does not decide that libraries stay out.

Disabling AST inference is likewise scoped: it applies only to a node that has an explicit saved contract. Every Code Node without one keeps inferring handles from code exactly as it does today.

### Sandbox limits are current values, not design constraints

The QuickJS sandbox has an output cap, a heap cap, a fetch budget, and no third-party libraries. Every one of those is a product decision that has already changed once and can change again — libraries were added in `a8221db7a` and removed in `7db9b4ccd`. This plan is built so none of it is load-bearing:

- Task 1.2 exports the capability manifest as **data read from `js-sandbox.ts`**, and prompts and help text are derived from it. Re-adding a library or raising a cap updates the generator with no change to this plan.
- No task hard-codes a limit value, and no acceptance criterion depends on a library being absent.
- Raising the caps or restoring libraries is separate work with its own tradeoffs — `7db9b4ccd` removed them to keep snippet behavior identical between dev and packaged Electron, and that concern has to be answered on its own terms, not folded into AI authoring.

Do not write the current values into prompts, docs, or tests as if they were permanent.

## Current gaps

- Inferred Code Node handles use `any`, so they do not solve type discovery.
- `NodeData.dynamic_inputs` exists in the frontend but is not persisted by `reactFlowNodeToGraphNode` or the protocol graph schema.
- Referencing an undeclared JavaScript identifier to create an input is not a suitable primary interaction for non-programmers.
- Editing code can silently add or remove handles.
- The editor assistant sees the document and language, but not the connected handles, expected destination type, graph context, or sample values.
- The assistant prompt advertises lodash, Day.js, Cheerio, CSV Parse, and Validator even though `packages/agents/src/js-sandbox.ts` states that they are unavailable.
- Editor chat returns free text. Creation needs an atomic response containing code, typed ports, title, and description.
- Snippet presentation currently uses frontend-only `NodeData.codeNodeMode`; it is not a runtime distinction and does not need to be solved by the AI authoring work in Phase 1.

## Product boundaries

### What the generator actually writes

A Code Node takes several typed inputs and produces several typed outputs, so "transformation" describes only one of the shapes users will ask for. Phase 1 generation covers **single-result data production over typed inputs**:

| Shape | Example |
|---|---|
| Reshape | `{first, last}` → `fullName` |
| Merge / join | zip two lists; join records on a key |
| Compute / derive | a score, a diff, a similarity between two inputs |
| Extract / parse | pull `id`, `status`, `payload` out of one response |
| Split / decompose | a record into typed fields; a list into `matched` and `unmatched` |
| Format / render | build a prompt or markdown block from data |
| Validate | rows → `{ valid, invalid }` |
| Seed / generate | no inputs → a fixture or config object |

Ordinary conditional logic is unrestricted throughout — `if`/`else`, `switch`, ternaries, and early returns are normal JavaScript. "Two lists, output the bigger one" is a plain single-output node.

### Phases 1–3 include

- AI authoring for an ordinary Code Node, across all of the shapes above.
- Stable typed input and output handles.
- Preview, test, repair, and conversational edits.
- Optional publishing as a reusable, versioned definition.

### Phases 1–3 exclude

- Calling arbitrary NodeTool nodes from JavaScript.
- Replacing subgraphs or workflow nodes.
- A new iterator, loop region, or correlation model.
- Converting arbitrary graph selections into code.
- User-installed JavaScript packages (see Phase 7).
- AI authoring for the other `nodetool.code.*` executors — Python, Bash, Ruby, Lua, Docker (see Phase 8).

The last two are deferrals, not permanent boundaries. Both are reached through the same Phase 1 mechanism — the per-runtime capability manifest — so neither needs a parallel generation stack.

### Reserved for later: conditional emission

Generated code always emits every declared output. Omitting an output key is meaningful — the kernel skips that edge, so downstream nodes on the untaken branch never fire, and `nodetool.control.If` branches by exactly this mechanism. Phase 1 does not generate it, for three reasons:

- `If`, `Switch`, `FilterCode`, and `Drop` already own workflow branching and are the better discovery target.
- Always-emitting outputs is what makes preview and the output-type warning meaningful; a handle that sometimes fires has no observable "expected" state to check against.
- Most routing requests are really partitions (`{ valid, invalid }`, one possibly empty), which are already expressible.

Adding it later means giving output ports an `optional` flag and relaxing the analyzer — a contract change, so it is recorded here rather than discovered as a bug.

The existing runtime decides how often a Code Node runs. A Code Node connected after `ForEach` receives the values produced by that iterator under the current correlation rules.

## Architecture decisions

### Keep one runtime node

Use `nodetool.code.Code` for both manual and AI-authored transformations. A second runtime node would duplicate sandbox limits, browser/server parity, serialization, and execution tests.

Do not persist `code_mode`, `is_transformation`, or another provenance flag. The runtime behavior of a Code Node does not depend on whether its source came from Monaco, an LLM, or a snippet.

An AI-authored node may retain optional `code_transform` metadata for later edits, but that metadata is authoring history, not a classifier or permission boundary. Removing it does not change execution. Editing generated code does not require a “convert to manual” operation.

### Add AI authoring without a new node state

Do not turn the current Monaco-first `CodeBody` into a large conditional component.

- Keep `CodeBody.tsx` as the code editor available to every Code Node.
- Add `CodeTransformationBody.tsx` as an optional compact contract summary when a Code Node has an explicit saved contract.
- Add `CodeTransformationDialog.tsx` for creation, preview, tests, and later edits.
- Open the same AI dialog from any Code Node, whether or not it has previous authoring metadata.

The compact summary shows the title, one-line description, typed handles, generation status, and actions for Ask AI, Test, and View Code. Monaco is lazy-loaded only when the user opens the code view. Users can edit code directly at any time without changing node identity or runtime behavior.

### Make the port contract explicit

When a Code Node has an explicit port contract, code is its implementation and does not redefine handles through incidental syntax.

```ts
interface CodeTransformationPort {
  readonly name: string;
  readonly type: SerializableTypeMetadata;
  readonly description: string;
}

interface CodeTransformationInputPort extends CodeTransformationPort {
  readonly required: boolean;
  readonly defaultValue?: unknown;
  readonly min?: number;
  readonly max?: number;
}

interface CodeTransformationSubmission {
  readonly title: string;
  readonly summary: string;
  readonly code: string;
  readonly inputs: readonly CodeTransformationInputPort[];
  readonly outputs: readonly CodeTransformationPort[];
}

interface CodeTransformationArtifact extends CodeTransformationSubmission {
  readonly schemaVersion: 1;
  readonly authoringPolicyVersion: string | null;
  readonly sandboxRuntimeVersion: string;
}
```

Persist the artifact across existing graph fields:

- `node.data.code`: executable source, as today.
- `node.dynamic_properties`: unconnected input defaults or sample-independent values.
- `node.dynamic_inputs`: a `Record<string, DynamicInputMetadata>` containing type, description, bounds, and default. Requiredness maps to the canonical type metadata's `optional` field instead of adding a second flag.
- `node.dynamic_outputs`: a `Record<string, DynamicOutputMetadata>` containing type and description.
- `node.ui_properties.code_contract`: contract schema version, `input_order`, and `output_order`. Its presence tells the editor that handles are explicit rather than AST-inferred.
- `node.ui_properties.code_transform`: optional authoring-policy version, sandbox-runtime version, original intent, and current summary.

Do not duplicate code inside `ui_properties`. Do not store transient preview samples or the authoring model on the node. Phase 2 saved test fixtures are explicit workflow content and are the only sample-data exception.

The generation artifact keeps ports as ordered arrays because order matters in the review UI. One mapper converts those arrays to the record-shaped graph fields and stores the name order in `code_contract`. When order metadata is absent, use record insertion order. `dynamic_properties` remains the source of runtime values; a default in `dynamic_inputs` describes the contract.

The original intent is saved authoring metadata and is included when a workflow or `.nodetool` bundle is shared. Label this in the UI and never store transient preview samples or a chat transcript. Export can later offer an authoring-history scrub without affecting execution.

AI generation stamps `authoringPolicyVersion` with the active policy. If authoring history is removed or a contract is created manually, later publishing reconstructs the artifact with `authoringPolicyVersion: null` and the current sandbox runtime version. Reusable definitions therefore do not require AI provenance.

AST inference remains available for Code Nodes without an explicit contract. It must not overwrite a saved contract, regardless of whether the code was generated or edited manually. Users may explicitly discard or re-infer a contract as a separate action.

### Use a structured generation service

Creation must not depend on extracting a code fence from a chat reply. Add a dedicated protected tRPC mutation that:

1. Accepts the instruction, typed inputs, optional expected outputs, bounded samples, current artifact when editing, and chosen language model.
2. Builds instructions from a canonical sandbox capability description.
3. Calls the existing runtime provider through `generateMessageTraced`.
4. Requires a `submit_code_transformation` provider tool call and validates its arguments as a `CodeTransformationSubmission` with Zod.
5. Passes the validated shape to the agents package, which checks JavaScript syntax and verifies returned object keys against declared outputs.
6. Stamps the accepted submission with server-owned schema, authoring-policy, and sandbox-runtime versions to create the persisted artifact.
7. Makes one repair request when the response is invalid.
8. Returns a discriminated error when generation still fails.

Keep provider resolution, secret access, tracing, and cost accounting in the backend. Keep prompt construction and response validation as pure functions in `@nodetool-ai/agents` so they can be tested without Fastify.

### Version the authoring instruction template

Phase 1 uses a system-owned instruction template assembled from four parts:

1. Sandbox manifest: runtime version, available globals, blocked APIs, and limits.
2. Type guide: NodeTool type names, reference shapes, and compatibility rules.
3. Code policy: local data computation for Phase 1, return-object convention, error behavior, and comments only where the reason is not clear from the code.
4. Metadata policy: an imperative title and one sentence describing the data change.

Give the assembled policy a version and return that version in the generated artifact. This makes generation regressions traceable when prompts change. A node may keep its original user intent for later edits, but it must not carry a replacement system prompt.

Phase 3 may add bounded, versioned `authoringInstructions` to a reusable transformation version, such as domain terminology or invariants. These instructions are user content below the system policy. They cannot add libraries, misrepresent available APIs, request secret values, or change application permissions.

### Model selection

Do not store the authoring model on a workflow node. It has no effect on workflow execution and would make the artifact depend on a UI preference.

Add an optional `code_model` entry to the existing model preferences:

1. Use the configured Code Generation model when present.
2. Otherwise use the active global chat language model.
3. Otherwise use the configured default `language_model`.
4. Fall back to the existing application default.

Settings shows “Code Generation” with a language-model picker and a “Use chat model” state. The transformation dialog shows the effective model and can change the Code Generation preference. It does not change the model used by the current chat thread.

Centralize this logic in `useCodeAuthoringModel`; components must not repeat the fallback chain.

### Keep Phase 1 generation focused on data reshaping

All Code Nodes retain the current runtime APIs, including `fetch`, `workspace`, `getSecret`, `sleep`, `uuid`, asset conversion, persistent `state`, and Code Node `yield` behavior. AI-authored code is not placed in a different sandbox.

The Phase 1 generation service supports local data reshaping only. Its prompt and static analysis reject obvious use of host APIs, persistent state, and `yield`, returning an unsupported-scope or unsafe-generation error with a suggestion to use an existing integration node or edit the Code Node directly. This is an authoring policy and quality check, not a runtime security boundary. Do not claim that generated code remains pure after a user edits it.

Phase 2 may support AI edits that deliberately use the full Code Node API. When an edit introduces network, workspace, secret, state, asset-conversion, or streaming behavior, show the detected capability change and require explicit confirmation before preview or apply. Static detection is advisory; a future enforceable permission model must be designed for all Code Nodes rather than inferred from transformation provenance.

### Preserve composition boundaries

| Concept | Owner |
|---|---|
| Local data reshaping | AI authoring for an ordinary Code Node |
| Reusable code-backed operation | Published transformation definition |
| Inline visual composition | Subgraph |
| Saved graph composition | Workflow node |
| Iteration and correlation | Existing `ForEach` and kernel semantics |

## Phase 1 — Create and run a typed AI transformation

**Outcome:** A user can add the existing `nodetool.code.Code` node from typed graph context, describe the change, generate a stable typed contract plus JavaScript, test it, and connect it without writing code.

### Phase 1 suggested landing order

```
1.1 ─┬─> 1.2 ─┬─> 1.4 ──> 1.5 ─┐
     └─> 1.3 ─┘                │
     └──────────────────────────┼─> 1.7 ─┬─> 1.8 ─┬─> 1.10
1.6 ─────────────────────────────┘        └─> 1.9 ─┘
```

Tasks 1.2 and 1.6 have no implementation dependency on 1.1 and can land in parallel. The diagram keeps 1.2 after 1.1 only as a review-friendly sequence. Tasks 1.8 and 1.9 are independent of each other once 1.7 lands.

### Task 1.1 — Persist typed dynamic inputs and authoring metadata

**Files:** protocol graph types and schemas, `NodeData.ts`, both graph converters, their tests.

- [ ] Add a recursive serializable type schema shared by dynamic inputs and outputs, plus enriched `DynamicInputMetadata` and `DynamicOutputMetadata` wrappers for direction-specific fields.
- [ ] Define the wire shape as `dynamic_inputs: Record<string, DynamicInputMetadata>` in protocol `Node`, `NodeDescriptor`, workflow Zod schemas, and frontend graph types. Do not persist the artifact's port arrays directly.
- [ ] Preserve input descriptions, defaults, and bounds already supported by `NodeData.dynamic_inputs`; map artifact `required` to `type.optional` and reject contradictory metadata.
- [ ] Extend dynamic output metadata with an optional description so artifact output descriptions survive save/load without changing handle type behavior.
- [ ] Define versioned `code_contract` UI metadata with `input_order` and `output_order`. Represent it as `NodeData.codeContract` and map it explicitly to and from `ui_properties.code_contract`.
- [ ] Define separate optional `code_transform` authoring metadata with authoring-policy version, sandbox-runtime version, original intent, and current summary. Represent it as `NodeData.codeTransform` and map it explicitly to and from `ui_properties.code_transform`.
- [ ] Treat `code_transform` as removable authoring history only. Adding, removing, or encountering an unsupported version must not change Code Node execution, available APIs, or whether its explicit contract remains active.
- [ ] Add one artifact-to-node mapper that converts ordered port arrays to dynamic-input/output records and restores display order from the stored name arrays.
- [ ] Round-trip all fields through ReactFlow-to-graph and graph-to-ReactFlow conversion.
- [ ] State beside the intent editor that the instruction is saved with shared and exported workflows.
- [ ] Add compatibility and malformed-data tests: non-array `type_args`, omitted legacy `type_args` normalized to `[]`, and future contract/authoring schema versions preserved but not interpreted by the corresponding UI.
- [ ] Add save/load regression tests with disconnected typed inputs and outputs, custom port order, defaults, and missing order metadata.

**Acceptance:** A transformation with no edges can be saved, reloaded, and display the same typed handles.

### Task 1.2 — Define the canonical sandbox capability manifest

**Files:** `packages/agents/src/js-sandbox.ts`, new shared manifest module, editor prompt construction, Code Node documentation.

The manifest is derived from what `js-sandbox.ts` already exports: the bridges `fetch`, `workspace`, `getSecret`, `uuid`, `sleep`, `assetToSandbox`, `sandboxToAsset`, `console`, and the limits `DEFAULT_TIMEOUT_MS`, `MAX_OUTPUT_SIZE`, `MAX_LOOP_ITERATIONS`, `MAX_FETCH_CALLS`, `GUEST_MEMORY_LIMIT`, `GUEST_STACK_LIMIT`. Read them from the module — never restate the values.

**Scope this to `nodetool.code.Code` only.** `nodetool.code.*` holds 19 nodes, and the others do not share this runtime: `ExecuteJavaScript`, `ExecutePython`, `ExecuteBash`, `ExecuteRuby`, `ExecuteLua`, and the `Run*Command` / `Run*CommandDocker` families run real interpreters in Docker or a subprocess, with Node builtins, image-provided packages, and a 10 MB output cap. A manifest describing "the Code Node runtime" without qualification would be wrong for all of them.

- [x] Correct the stale `code-node.ts` header docstring, which described the engine as Node's `vm` module rather than QuickJS WASM. *(Done 2026-07-21.)*
- [ ] Export one serializable manifest for the existing globals, async APIs, memory/output/time limits, and runtime version.
- [ ] Define the narrower Phase 1 generation policy separately from the runtime manifest. The policy may reject APIs that remain valid in an ordinary Code Node.
- [ ] Derive Code Node help text and LLM instructions from the manifest rather than maintaining separate lists.
- [ ] Remove unavailable libraries from `useChatIntegration.ts` and `SANDBOX_GLOBALS` in the inference utility unless the runtime actually exposes them.
- [ ] Add a test that fails when authoring instructions advertise a missing runtime API.
- [ ] Add tests showing the generation policy's blocked list is a subset of real runtime capabilities and is described as an authoring restriction, not an unavailable API.
- [ ] Keep existing browser/server sandbox parity and bridge-name protection unchanged.
- [ ] Add a runtime-version field for later reusable transformation snapshots.

**Acceptance:** Runtime help, capability manifests, and sandbox tests agree on every available API; generation prompts label narrower authoring-policy exclusions without claiming those APIs are absent from Code Nodes.

### Task 1.3 — Add shared transport schemas

**Files:** new protocol schema module and tests.

- [ ] Define separate `CodeTransformationSubmission` and server-stamped `CodeTransformationArtifact` schemas, plus request, input/output port, and discriminated error schemas with Zod.
- [ ] Restrict port names to valid, non-reserved JavaScript identifiers.
- [ ] Restrict types to NodeTool’s serializable type metadata shape.
- [ ] Require one or more outputs and unique names within each direction.
- [ ] Allow defaults and numeric bounds only on input ports; validate defaults against their declared types before applying an artifact.
- [ ] Give output ports no `optional` flag in Phase 1. Every declared output is emitted on every return path, so a generated node always fires all of its output edges. Record this as a deliberate scope decision, not an oversight: omitting an output key is valid Code Node behavior that the kernel uses for branching (`runner.ts` skips the edge when a key is absent; `nodetool.control.If` branches by exactly that mechanism), and Phase 2 may add optional outputs to express it.
- [ ] Add a pure, bounded `valueMatchesSerializableType` helper in protocol, porting the existing `TypeHandler.ts` value-match test vectors without importing frontend code. Use it for artifact defaults.
- [ ] Set request limits for instruction length, number of ports, sample count, sample byte size, and code length.
- [ ] Define an optional destination contract so generation can target an existing input handle exactly.
- [ ] Normalize model aliases such as `string` to the canonical NodeTool type name only in one place.
- [ ] Keep this package limited to transport and data-shape validation. Do not add a JavaScript parser or generation policy to `@nodetool-ai/protocol`.

**Acceptance:** Malformed requests and artifact shapes are rejected at the transport boundary.

### Task 1.4 — Implement structured artifact generation

**Files:** `packages/agents/src/code-transforms/*` and tests with a scripted provider.

- [ ] Build a short system prompt describing the task, contract rules, sandbox, allowed syntax, comment policy, and submission tool.
- [ ] Include input names, NodeTool types, descriptions, and bounded samples.
- [ ] Include the exact expected output when generation starts from a destination handle.

## Phase 7 — User-declared capabilities and libraries

Let a Code Node declare what it needs — network, workspace, secrets, persistent state, and **named third-party libraries** — instead of the runtime deciding for all nodes at once. This is the "general Code Node capability system" the Phase 1 runtime policy points at, and libraries are one capability inside it, not a special case.

- Declared capabilities live on the node and drive both the runtime surface it receives and the manifest the generator reads. A node that declares `dayjs` gets `dayjs` in the sandbox and in the prompt; a node that declares nothing keeps today's lean surface.
- This resolves the tension `7db9b4ccd` created: libraries were stripped so every snippet behaves identically between dev and packaged Electron. A declared, per-node, versioned dependency set is answerable to that concern in a way a blanket always-on library bundle was not — the packaging question (which libraries ship, how they resolve offline in Electron) is the real design work here, not the API.
- Capabilities are declared data, never inferred from AI provenance. A hand-written node and a generated one reach them the same way.
- AI edits that add a capability surface it through the advisory `capabilityChanges` path from Phase 2 and require confirmation before preview or apply.
- Security follows capability, not authorship: an enforceable permission model, if built, gates on the declared set for **all** Code Nodes.

Do not start this before the Phase 1 manifest is genuinely per-runtime data. If the manifest is still a single hard-coded description, libraries have nowhere to plug in.

## Phase 8 — AI authoring for the other code executors

Extend AI authoring from `nodetool.code.Code` to the rest of `nodetool.code.*` — `ExecutePython`, `ExecuteBash`, `ExecuteRuby`, `ExecuteLua`, and the Docker executors. They already share the Monaco body; what they lack is a generator that understands their runtime and their output shape. Most of Phase 1 is reused, not rebuilt:

- **Manifest per runtime (already the Phase 1 shape).** Each executor gets its own capability manifest — Python builtins and pip packages, Bash utilities, the Docker image's contents. The generator selects the manifest by node type. This is why 1.2 is scoped to `nodetool.code.Code` rather than hard-coding one runtime: the seam is already there.
- **Analyzer per language.** 1.4's JavaScript analyzer (acorn) becomes one of several; Python needs its own parser and return-contract check. The tool-call transport, repair loop, telemetry redaction, and model selection are language-independent and carry straight over.
- **Contract shape differs, and this is the hard part.** These nodes emit `stdout`/`stderr`, not typed handles. Either teach them a typed-output protocol (a documented stdout-JSON convention the runner parses into handles) or accept that their contract is looser than `Code`'s. Decide this explicitly; do not paper over it by pretending they have `Code`'s contract.
- **Docker executors intersect Phase 7.** "Which libraries are available" for a Python node is exactly a declared-capability question, so Phase 8 for the Docker families depends on Phase 7's dependency model.

The Phase 1 exclusion of "Python or shell generation" is lifted here, deliberately and per-runtime — not by loosening the `Code` generator.

## Phase 1 design-review defaults

These are the recommended defaults. Change them during design review only when a tested user flow or runtime constraint gives a concrete reason.

1. Expose separate “Write Code with AI” and “Code” entry points. Both instantiate the same ordinary `nodetool.code.Code`; the entry point leaves no persisted mode. Keep the AI label broad and carry discovery through search aliases, because the generator covers reshaping, merging, computing, extracting, formatting, validating, and seeding — not only transformation.
2. Validate scalar, list, dictionary, union, optional, and reference discriminators without loading referenced assets. Treat opaque custom types structurally and cap traversal depth and element count.
3. Show the latest-run sample summary before sending it and require consent the first time. Remember the preference locally; allow per-generation exclusion.
4. Keep Phase 1 generation focused on local data reshaping. Reject obvious host API, `state`, and `yield` use in generated proposals, while documenting that later edits run with the normal Code Node API and are not runtime-restricted.
5. Store one global Code Generation preference, with “Use chat model” as the default. Allow an unsaved dialog override only after a user asks for it; do not add it preemptively.
