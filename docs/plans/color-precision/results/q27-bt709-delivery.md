# BT.709 delivery owner decision evidence

Owner decision, 2026-11-05: **keep pass-through with today's BT.709 tag (O1)**. Delivered values are not converted. The inaccurate transfer tag is accepted.

The study recommends O1 for the existing appearance-preserving delivery contract. O1 matches the intended sRGB source in the Chromium-like sRGB model and is closer than O2 in the BT.1886 model. O2 is the right mathematical round trip only for a player that inverts the BT.709 OETF. It is not a general appearance correction for SDR video players. This recommendation accepts O1's transfer-tag mismatch. It does not certify O1 as strict sRGB-to-BT.709 encoding.

Confidence: high in the direction of the simulated change and the transfer mathematics, moderate in the product recommendation. This is a transfer-only still-image study, with verified synthetic content and explicit player models. It is not a monitor measurement, browser playback test, perceptual user study, or new codec qualification. Audience player distribution is unknown.

## Method

The study implements the transfers directly, using double precision. For encoded source channel S:

```
L = S / 12.92                         if S <= 0.04045
L = ((S + 0.055) / 1.055)^2.4          otherwise
O1 = S
O2 = 4.5 L                           if L < 0.018
O2 = 1.099 L^0.45 - 0.099              otherwise
```

For display simulation O2 is rounded to the nearest 8-bit full-range RGB code, O1 retains the source's 8-bit codes. The inverse-709 curve uses V/4.5 below 0.081 and ((V+0.099)/1.099)^(1/0.45) above it. The rounded BT.709 constants introduce a very small discontinuity at the knee. The 256-code round-trip check avoids that gap. Checks also pin sRGB 0.5 to linear 0.2140411405 and its BT.709 encoding to 0.4501885294.

Images are oriented and normalised to sRGB, then capped at 1024 pixels wide without enlargement to keep memory modest. Sharp's default Lanczos3 resize occurs in encoded sRGB before analysis. Statistics cover every resulting pixel. Charts are not numerical inputs. The 8-bit study is not a recreation of A98's codec round trip. ProRes 10-bit quantisation would reduce the small inverse-model residual, but would not remove the systematic transfer change. No YUV matrix loss, chroma subsampling, limited-range quantisation or lossy compression is included.

Code differences are absolute channel differences, pooled across R/G/B within a pixel's **source linear luminance** band. Shadows: Y<0.1. Mids: 0.1<=Y<0.5. Highlights: Y>=0.5. Y=0.2126R_linear+0.7152G_linear+0.0722B_linear. These are linear-light thresholds, not thirds of encoded code space. Max/p99 are channel errors, not Y-code errors. Code units are full-range 8-bit RGB equivalents, not limited-range video Y codes.

### Playback models and primary evidence

**P1: sRGB / Chromium-like.** Display linear RGB is sRGB_decode(V). In Chromium tag 143.0.7499.155, `ColorSpace::GetTransferFunction` explicitly maps BT709 to the sRGB transfer. This supports the model for that colour-conversion path, not every browser build, OS compositor, hardware overlay or decoder route. [Chromium source, lines 926–942](https://chromium.googlesource.com/chromium/src/+/refs/tags/143.0.7499.155/ui/gfx/color_space.cc#926).

**P2: BT.1886 reference display.** Display linear RGB is V^2.4, at zero black and 100 cd/m² white. Actual BT.1886 includes black/white-dependent coefficients, so this is its infinite-contrast case, not every physical TV. [ITU-R BT.1886, Annex 1, PDF page 4](https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.1886-0-201103-I!!PDF-E.pdf). A colour-managed player can also use this interpretation and reproduce P2 on a calibrated display.

**P3: colour-managed inverse-709 hypothesis.** Display linear RGB is inverse_BT709(V), then encoded for an ideal calibrated sRGB display. This is an explicitly selected mathematical interpretation of the tag, not a confirmed major-player default. It is included to show the condition under which O2 reproduces the source. Colour management does not itself require inverse-709: the source profile and viewing intent choose the transfer. [ITU-R BT.709-6, Table 1.2, PDF page 5](https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.709-6-201506-I!!PDF-E.pdf) defines the OETF. Its footnote also describes adjusting production encoding while viewing through BT.1886. Therefore an OETF followed by BT.1886 is deliberately not a linear identity system.

The [mpv manual](https://mpv.io/manual/stable/#video-filters-format) documents BT.1886 for automatic YCbCr transfer selection and colour management overrides. Its [SDR gamma-adjustment option](https://mpv.io/manual/stable/#options-sdr-adjust-gamma) also describes passing SDR through on sRGB targets unless adjustment is requested. This gives primary evidence that player configuration matters. It does not prove any one model matches all mpv defaults/platforms. The [W3C sRGB conversion sample](https://www.w3.org/TR/css-color-4/#color-conversion-code) supplies the sRGB reference formula.

I could not confirm a universal Safari, QuickTime, Firefox or desktop-player response. Chromium's source mentions an Apple gamma approximation, but that comment is not sufficient first-party Apple evidence and was not treated as an Apple playback specification. No installed-player output was sampled. ICC profiles, ambient adaptation, finite black, OS colour settings, HDR desktops and user picture modes remain outside this study.

### Error from intended sRGB source

Method: **absolute linear luminance error**, not CIEDE2000. Each pixel's displayed Y is compared with its sRGB-decoded source Y. Units are percentage points of reference white. At the assumed 100 cd/m² white these numbers also equal cd/m². They are not relative percent errors and not perceptually uniform colour distances. Bias is signed mean displayed-minus-source Y. The bright background moves less in codes, but its luminance error can still exceed that of darker pixels. A fixed code shift is not a fixed light difference.

## Visible consequences

F1: In the dark room, O2 deepens the stone and ceiling shadows and reduces visible separation in already dark surfaces in P1/P2. It does not literally clip all those values to zero. O1 preserves the source in P1 and already darkens it somewhat in P2.

F2: In the portrait, O2 visibly darkens the face, neck and grey background in P1/P2. The change is broad tonal shading, not primarily edge noise or codec damage. Mean luminance falls by 3.923 reference-white percentage points in P1 and 6.005 in P2, versus 0 and 2.133 for O1.

F3: In the sky, O2 darkens the cloud field and foreground rocks in P1/P2. This experiment does not measure new contouring over time or compression artefacts. In the bright product frame, the background remains bright but becomes greyer, and the cup's dark regions become denser.

F4: P3 reverses the conclusion. O1 looks lighter and more washed out than the source. O2 restores the source closely. A managed player that uses a BT.1886 source interpretation instead follows P2. There is no single colour-managed appearance without naming that interpretation.

## Export scope and D5 compatibility

Code evidence: `packages/video-nodes/src/nodes/timeline/outputFormats.ts` lines 137–145 and 167–240, `rawFrames.ts` lines 562–577, and `native/timeline/src/export/ExportEngine.cpp` lines 132–141 and 340–371. The server sets a BT.709 matrix/range scaler and BT.709 metadata for MP4, WebM/VP9 and MOV/ProRes. Native sets BT.709 metadata and performs RGBA-to-YUV with libswscale. Neither inspected path applies the sRGB decode/709 encode studied here.

A delivery-boundary O2 implementation would change re-encoded timeline MP4/H.264, WebM/VP9 and MOV/ProRes video from the inspected server format resolver, plus encoder overrides that take the same BT709_ARGS path and native video output if implemented there. It would affect photographic clips, generated media, text, graphics and effects after compositing, not only video source clips. Alpha is coverage and must not receive this RGB transform. Exact alpha-route support still needs qualification.

PNG-sequence branches bypass those video encoder arguments on server and native. A conversion scoped to video delivery would not change PNG stills, PNG sequences, editor previews, audio-only exports, stored source assets or existing exported files. This is scoped to the inspected timeline routes, not a claim about every video node or third-party exporter in the monorepo.

An unconditional change in a shared encoder would change the output of an existing document when re-exported, even if its stored JSON and preview stayed identical. That violates the plan's S6/D5 promise: absent or version 1 keeps today's rendering, A99–A102 change rendering only at version 2, and A102 explicitly requires old decoded exports to remain within declared tolerances. A 16-code transfer shift is not a codec-tolerance detail.

D1: Keep O1 for absent/version 1 documents. Do not repair their metadata mismatch by silently changing pixels.

D2: The owner chose O1 for delivery. Any future proposal for O2 at version 2 would need to gate delivery conversion with the document's version and qualify the complete preview/export contract. A version upgrade is explicit, takes a prior snapshot, and unsupported routes must refuse pixels under D5.3/D5.4. The same display shift remains possible even with linear working pixels, so version 2 is not evidence that strict OETF conversion is perceptually preferable.

D3: If accurate transfer metadata is a separate product requirement, record that separately from source appearance. The binary O1/O2 choice does not offer universal player matching. Broadcast appearance matching would require a specified viewing transform or mastering target, rather than assuming that O2 alone reproduces an sRGB master on a BT.1886 display.

Plan evidence: [D5 and S6/A99–A102](../high-precision-media-processing.md) and [S1 owner closeout](s1-runtime-interfaces.md#s1-owner-closeout). This copy records the subsequent O1 owner decision. The numerical study is unchanged.

The three O1 cases pass on both adapters. They assert BT.709 transfer, matrix,
primaries and limited-range tags through `videoStreamFormat`. An independent
unconverted source encode measures codec loss, capped at 2 codes for H.264/VP9
and 0 for opaque ProRes, based on the ramp round trips. Delivery must match the
unconverted source within that measured loss plus one code for RGBA8 render
rounding. A strict transfer conversion's 16–17-code shift cannot pass this bound.

Before restoring expected-failure markers, B215, B216 and B217 were each run
as ordinary tests on lavapipe. That run exited 1 with exactly those three
failures, 16 ordinary passes and the three original transfer expected failures:

- F1: B215 reached the profile-normalization assertion, 55 codes versus 2.
- F2: B216 reached the default-decoder alpha assertion, 255 codes versus 1.
- F3: B217 failed at `encoder.finish()` while writing the first HEVC packet:
  `Failed to write packet: Not yet implemented in FFmpeg, patches welcome`.

B215 and B217 retain `it.fails` and their original assertions. B216 now uses
`readRgbaFramesWith` with `libvpx-vp9` for input and both delivery branches,
retaining its one-code alpha bound. Its complete route passes on lavapipe.
The default-decoder limitation remains in the backlog. This change qualifies
that explicit decoder, without changing production decoding or qualifying all
players.

NVIDIA's six PNG/WebP profile cases and MOV alpha case still fail the RGBA8
low-alpha render assertion at 255 codes versus 1, as recorded in B218. With
VP9 alpha now decoded correctly, that route reaches the same render failure.
Its alpha-decode assertion passes. No B218 correction or tolerance change was
made.

No ffmpeg or ffprobe binaries were spawned. Media encoding, decoding and stream
inspection use the runtime media APIs in process. No dependency rebuild was
needed. `test:affected`, root typecheck, root lint, `harness gate`, `/verify`
and full suites were not run, as requested. Source oxlint was not run because
no source files changed.
